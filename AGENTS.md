## Product and stack

- Choreograph is an AI front desk and scheduling product for service businesses. Its Try demo experience uses Juniper Cleaning, one fictional cleaning company, to show the complete guest customer→coordinator request, document-grounded guidance, quote, review, booking and CRM-sync story. Keep the product brand distinct from the demo company; this positioning does not expand v1 into multi-business onboarding, multiple industry demos or a generic workflow engine.
- Next.js/React/TypeScript frontend; Python/FastAPI API; PostgreSQL with pgvector on Google Cloud SQL; LlamaIndex Python retrieval adapter; OpenAI adapter; optional visitor-owned HubSpot OAuth; Cloud Run and Cloud Tasks. The selected paid database is deliberate. Do not replace it with Supabase/Firebase/Neon or a production SQLite file by default.
- The visual assistant is the primary product workspace. Help visitors test without inventing prompts: keep three job starters, a browsable bank of at least eighteen useful questions and contextual follow-ups in fake and live modes, including busy-first-choice, open-week, cleaning-supplies and methods questions. Use interactive service/clarification/source/quote/week cards with flexible free text and a reachable composer. Selections prepare the same draft/commands; explicit Send/review/approval still applies. For RAG answers show the actual cited document/page in a right-hand desktop pane with the supported passage highlighted and a readable narrow-screen reader. A decorative excerpt is not live retrieval evidence.
- Use each visitor's detected, server-validated local IANA timezone as their isolated workspace's scheduling zone; persist it across refresh/OAuth, interpret hours/relative dates there and store instants in UTC. No fixed New York business zone or silent appointment shifts after a device-zone change. Detection failure needs a timezone choice before scheduling. See blueprint section 7.1.
- Seed a persistent mixed fictional calendar. The guided initial busy path must show an occupied requested working date and a valid alternative; the open-week shortcut shows a full seven-day availability card. Seed/materialize once before availability is exposed, never move blockers after queries/refresh or displace existing guest bookings. Chat and Business view use the same records; full duration and staff eligibility determine availability. Calendar cards update the draft, never reserve automatically. See sections 5.1/7.2; no extra mobile Figma frames are implied.
- No mandatory visitor signup. Use a scoped, expiring guest workspace and safe server-side session authorization. Customer/coordinator switching is a synthetic demo role, not production employee identity.
- Business-document RAG is in v1: author original fictional Juniper service/policy guides as actual text-based PDF assets plus a short Markdown FAQ, with inspectable real page/section sources and bounded optional guest document replacements. The six canonical sources, pipeline and actual reader are implemented; real-provider quality acceptance is outstanding. Fictional content must be labelled; configured live answers must retrieve actual stored passages rather than return canned sample answers. Keep it in the ordinary enquiry→booking flow, with a compact Documents area in Business view. No visitor upload is required to try the sample.
- Public CRM choices are Connect your HubSpot and Continue without CRM. The skipped path makes no HubSpot calls or CRM outbox work and never secretly uses an operator account. Optional OAuth must bind the visitor's selected account/session, disclose synthetic exports and offer native record links only after real verification. Respect unlisted-app install limits, account permissions and unverified-app confirmation; do not claim unlimited connections or substitute a generic recording for native verification.
- Track distinct HubSpot account installations separately from guest sessions/tokens; show safe private operator counts and a public capacity-unavailable fallback to Continue without CRM. HubSpot supports real API uninstall; deleting a token is not uninstall. Verify slot-release timing/current support, disclose HubSpot admin notifications, protect other active uses of the same account and clean only app-created records while authorization exists. Automatic expiry uninstall needs an explicit disclosed policy, not a hidden timer. See blueprint section 12.2.
- No payments, real outreach, Google Calendar, separate vector service or extra agent/workflow framework is required for v1.
- Dependencies are pinned. Keep live model/version, dimensions, tokenizers and rates unset until current official support, compatibility and pricing are verified. Do not copy a sibling's keys, fixed model or runtime settings.
- Carry SQLAlchemy + Alembic as the recommended persistence baseline, aligning with LlamaIndex's PostgreSQL adapter and keeping one ORM ecosystem. Verify compatible versions/driver configuration during implementation; do not add Tortoise/Piccolo/SQLModel or repeatedly reopen the baseline merely for a bundled interface. See blueprint section 10.2.

## Engineering boundaries

- Use one Next.js frontend with a narrow server bridge and one Python/FastAPI backend codebase, including shared worker handlers/local runner. Alembic is a schema-release tool, not another backend; HubSpot stores the reviewed CRM summary, not the authoritative reservation.
- Backend domain code owns exact cents/minutes, quotes, availability, booking transitions and approval. UI and assistant use the same commands.
- LlamaIndex handles bounded ingestion/retrieval; the assistant uses retrieved passages only for business guidance. Catalogue rules, current booking records and actual integration receipts remain authoritative. Insufficient/conflicting evidence needs an honest answer or review, not an invented policy.
- Authorize document search/previews through the server-owned guest manifest and ready versions. Metadata filters alone are not authorization. Treat documents as untrusted content; preserve actual source/page mapping and evaluate support. Replacement is atomic, failed replacement preserves the ready version, and reset/expiry retires indexing effects and cleans guest source bytes/chunks/embeddings.
- PostgreSQL must enforce concurrent overlap protection. Preserve old reservations on failed reschedules. Use workspace-scoped relationships, version checks and idempotency.
- For authorized connected CRM exports, commit the reservation and destination-bound outbox work together. Skipped CRM has no CRM work. Cloud Tasks delivers; the outbox and account/connection/workspace-scoped mappings support recovery. Repeated delivery, late revisions, expiry, destination changes and ambiguous external creates must be safe and honest.
- Visitor HubSpot access/refresh tokens and the app client secret stay in protected server-side storage. A separate operator-controlled test account may use a supported static token in server-only ignored `.env.local` locally or Google Secret Manager on deployment for specifically authorized acceptance; it is never a fallback for a skipped/denied/failed visitor connection. No public CRM proxy, shared operator login or app-sent email/SMS outreach. HubSpot's own admin uninstall notification must be disclosed; it is not an app-sent campaign. Touch only explicitly created demo records. Verify account scopes, upsert/uniqueness and cleanup support; revocation can prevent cleanup and must be reported honestly.
- Keep a small provider/tool vocabulary. Model output cannot run SQL, arbitrary HTTP, shell commands, confirm prices or invent successful actions.
- Pydantic/OpenAPI own API schemas; generate narrow browser types rather than hand-maintaining divergent business contracts. Keep the Python domain independent of FastAPI/vendor startup.
- Preserve useful private diagnostics with fixed codes/counts/opaque references. Never log raw requests, contact data, model payloads, cookies or secrets.
